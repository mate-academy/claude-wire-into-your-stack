# Notes

**Server.** Connected the `docs` MCP server — `@modelcontextprotocol/server-filesystem` scoped to `${CLAUDE_PROJECT_DIR}/docs`, committed in `.mcp.json`. It's useful here because `docs/api.md` is the API reference for the routes Claude edits, and keeping the two in sync depends on Claude actually being able to read the doc, not just the code. The permission rule in `.claude/settings.json` allows only `mcp__docs__read_file` and `mcp__docs__list_directory` — read-only, since there's no legitimate reason for this server to write files. Used it live: had a headless run read `docs/api.md` through the server and list its documented endpoints, then cross-checked that against the actual route code (no drift found).

**Skill.** `add-crud-resource` (`.claude/skills/add-crud-resource/SKILL.md`) captures the repeated shape every resource in this API follows — store helpers in `db/store.js`, a route file with the project's exact `400`/`404`/error-shape conventions, the `server.js` mount, and a mirrored test file — as seen in the `users` resource. The description names the trigger phrases explicitly ("add a products resource", "create an orders route", "scaffold a new resource for X") and an explicit exclusion ("Do not use for unrelated route tweaks, bug fixes, or non-CRUD endpoints") so it fires precisely. Confirmed: asked a fresh session "I want to add an orders resource, what do I need to do?" without naming the skill — it identified and cited the skill by name and reproduced the four-part scaffold correctly. A negative test (a README typo-check request) did not trigger it.

**Command.** `/check-conventions [resource]` (`.claude/commands/check-conventions.md`) audits a resource — or all of them, if no argument is given — against the same conventions the skill authors: route/mount structure, store-only data access, validation status codes, error shape, test coverage, and doc accuracy. It's worth a shortcut because it's the natural pre-commit/PR-review check on this small API, and complements the skill: the skill authors new resources correctly, the command verifies any resource (new or old) still holds the line. Ran it once against `users` — all 6 checks passed with exact file:line citations.

**Hook.** One `PostToolUse` hook on matcher `Edit|Write` (`.claude/settings.json`) — reacts after a file changes rather than blocking the edit, since lint issues are worth fixing, not worth stopping work over. It runs `npx eslint --fix` on the touched file if it's `.js`. Chose react-not-prevent because auto-formatting is safe to apply after the fact; a `PreToolUse` guard is better reserved for genuinely destructive actions, not style. Triggering it on purpose surfaced a real, unrelated gap: this checkout had never had `npm install` run, so the hook's `npx eslint --fix` pulled a mismatched fresh ESLint that couldn't resolve `eslint.config.js`'s `@eslint/js` dependency. Ran `npm install` to fix it (gitignored, nothing added to the commit) — after that, the hook ran cleanly and a manual check with the same command confirmed it correctly flags real violations (e.g. an unused variable) in edited files.

**Headless run.** Ran `/check-conventions` (no argument, so it audits every resource) via `claude -p`, locked to `--allowedTools "Read,Glob,Grep"` — no `Write`, `Edit`, or `Bash`, since an audit only needs to read files, never change them. That tight scope is exactly why it was safe to run unattended: even a misbehaving prompt couldn't touch the repo. It found a real gap: `health` has no `tests/health.test.js`, unlike `users` — 5/6 checks passed for `health`, with the missing-test-file failure cited precisely.
