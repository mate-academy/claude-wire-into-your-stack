# Notes on wiring Claude into this repo

**Server.** Connected the official filesystem MCP server (`@modelcontextprotocol/server-filesystem`) scoped to `./docs`, at project scope in `.mcp.json`. It's credential-free and genuinely useful here: `docs/api.md` is the source of truth for the API shape, so Claude should read it directly rather than re-deriving it from route code. The permission rule in `.claude/settings.json` allows only `mcp__docs__read_text_file` and `mcp__docs__list_directory` — the two read-only tools actually needed — not the server's write/edit/move tools. Used it with `claude -p --mcp-config .mcp.json --allowedTools "mcp__docs__read_text_file,mcp__docs__list_directory" "..."` to list `docs/` and summarize the endpoints in `docs/api.md`; it worked correctly.

**Skill.** `.claude/skills/add-route/SKILL.md` captures the one pattern this project repeats for every resource: add store helpers to `db/store.js` first, add a `routes/<resource>.js` router with `GET /`, `GET /:id`, `POST /`, `PUT /:id` following the `400`/`404`/`{ "error": "message" }` conventions from `CLAUDE.md`, mount it in `server.js`, mirror `tests/users.test.js`, and document it in `docs/api.md`. The description is scoped to "adding a brand-new resource/endpoint" and explicitly excludes editing existing routes, so it doesn't fire on unrelated work. Confirmed it fires: asked headless Claude (without naming the skill) to "add a new 'notes' resource... list, get, create, update," and it produced exactly the store-first/route/mount/tests/docs pattern, all tests passing. That demo change was reverted afterward — it was only proof the skill fires, not part of this PR.

**Command.** `.claude/commands/review-checklist.md` reviews the current uncommitted diff against the conventions in `CLAUDE.md` (route-per-file, store-only data access, 400/404 validation, error shape, docs parity), then runs `npm test` and `npm run lint` and gives a verdict. Worth a shortcut because it's the exact check worth running before every commit, and typing it out each time is wasted effort. Took `$ARGUMENTS` so it can be scoped to specific files. Ran it once against the notes-resource diff produced above; it correctly reported all conventions as passing and both test/lint as green.

**Hook.** `.claude/hooks/guard-commit.js`, wired as a **PreToolUse** hook on the `Bash` matcher in `.claude/settings.json`. It **prevents**: whenever a Bash command contains `git commit`, it runs `npm test` first and blocks the commit (exit code 2) if the suite is red, before the command ever executes. This is the standard that should never be optional: broken code shouldn't even make it into a local commit, let alone the shared branch. Chose PreToolUse over PostToolUse specifically because the local ESLint config here only has `eslint:recommended` (no stylistic rules), so a "format after edit" hook had nothing reliably fixable to demonstrate — a commit guard is deterministic and easy to prove. Verified both directions: deliberately broke `tests/notes.test.js` (`assert.equal(res.status, 999)`) and attempted `git add -A && git commit -m ...` via headless Claude — blocked, nothing staged, hook's stderr message shown. Fixed the assertion, retried — allowed, files staged as expected.

**Headless task.** Ran the "add a notes resource" task above with `claude -p --allowedTools "Read,Write,Edit,Glob,Grep,Bash(npm test:*),Bash(npm run lint:*)"`. Locked it down to exactly the tools that task needs: file read/write/edit and search, plus two narrowly-scoped Bash allowances (`npm test`, `npm run lint` only — no general `Bash(*)`, no git, no network). It completed the task unsupervised, ran the test/lint commands itself to confirm, and reported back cleanly.
