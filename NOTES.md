# Wiring notes

**Which server did you connect, why is it useful here, and what did your permission rule allow?**
I connected the `docs-fs` server — the MCP filesystem server (`@modelcontextprotocol/server-filesystem`), pointed at this repo's `docs/` folder (`.mcp.json`, project scope, no credentials needed). It's useful because `docs/api.md` is the source of truth for this API's contract, and route work regularly needs to read or search it — this gives Claude direct, scoped access instead of guessing at conventions. The permission rule in `.claude/settings.json` allows exactly three read-only tools — `mcp__docs-fs__read_text_file`, `mcp__docs-fs__list_directory`, `mcp__docs-fs__search_files` — nothing that writes, and `.mcp.json` only exposes the `docs/` directory to begin with, so there's no path to anywhere else in the repo through this server.

**What repeated way of working did your skill capture, and how did you word the description so it fires?**
The `express-route` skill (`.claude/skills/express-route/SKILL.md`) captures this project's one consistent shape for adding/changing a route: data access only through `db/store.js`, the validate-then-404-then-succeed handler order, the `{ "error": "message" }` error format, and the matching test-file structure in `tests/`. The description names the trigger phrases directly — "add a route", "add an endpoint", "add a DELETE/PATCH for X", "new resource", "add a store method for X", "write a test for this route" — and explicitly excludes non-Express work (docs-only edits, CI config) so it doesn't fire outside its lane. Confirmed it fires: asking for a DELETE endpoint and a bulk-create endpoint (without naming the skill) both invoked it, and the resulting route/store/test/docs changes matched the skill's conventions exactly.

**What command did you add, and what makes it worth a shortcut?**
`/check-route` (`.claude/commands/check-route.md`), taking a file path via `$ARGUMENTS`. It reviews a route file against this project's 8-point checklist (router export, store-only data access, input validation, 404 handling, error shape, status codes, no module-scope mutable state, mounted in `server.js`) and reports a pass/fail/warn checklist with a one-line verdict. It's worth a shortcut because it's the same review I'd otherwise redo by hand after every route change — saving it behind a command makes it a one-line habit instead of a mental checklist.

**What hook did you set — does it react or prevent, and on which event?**
A `PreToolUse` hook on the `Bash` matcher (`.claude/settings.json` → `.claude/hooks/guard-rm-rf.js`) — it *prevents*, not reacts: it inspects `tool_input.command` before the shell ever runs it, and denies anything matching a recursive force delete (`rm -rf`, `rm -fr`, `rm -r -f`, `--recursive --force`, in any flag order). Ordinary commands, including plain `rm <file>`, pass through untouched. Verified live: created a scratch file, ran `rm -rf` on its directory through the Bash tool, and the hook blocked it with its deny reason before anything was deleted; the file was still there afterward.

**What did you run headless, and what did you lock down?**
Ran the test-and-lint verification for this repo headless: `claude -p "Run the test suite and the linter ... Do not modify any files." --allowedTools "Bash(npm test),Bash(npm run lint)"`. It came back with 11/11 tests passing and a clean lint run. I locked the tool allowlist down to exactly those two commands — no `Edit`, no `Write`, no general `Bash` access — so the task could report on the repo's health but had no way to touch any files, even accidentally.
