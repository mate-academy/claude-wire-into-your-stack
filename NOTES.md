# NOTES

**Server:** Connected a filesystem MCP server (`docs`) scoped to `./docs`. It's useful here because the repo already keeps an API reference (`docs/api.md`) that Claude should treat as the source of truth when adding or checking routes — this gives it a direct, read-only line to that file instead of relying on whatever happens to already be in context. The permission rule only allows `read_text_file`, `list_directory`, and `list_allowed_directories` — no `write_file`/`edit_file`/`move_file` — so the server can inform Claude but can't use it to change the docs on its own. Confirmed it works with a headless run that read `docs/api.md` through the server and correctly summarized its structure.

**Skill:** Captured the route-writing convention this repo repeats: one router per resource, all data access through `db/store.js`, `400` on bad input / `404` on a missing record, and errors always shaped as `{ "error": "message" }`. The description is scoped to "adding, writing, or modifying an Express route/endpoint in this repo" so it fires on that specific kind of request rather than on generic questions about the codebase. Confirmed it fires: asked Claude to sketch a new `orders` route without naming the skill, and it reproduced every convention (store indirection, 400/404 split, error shape) unprompted.

**Command:** Added `/new-route <resource>`, since scaffolding a new resource is the single most repeated multi-file task on this API (store helpers + router + server.js mount + test, four files every time). It takes the resource name as `$1` and scaffolds all four pieces in one pass, following the same conventions as the skill. Ran it once with a throwaway `widget` resource — it created working store helpers, a router, the `server.js` mount, and a passing test (`npm test` went 5 → 8 tests, all green) — then reverted the scaffold since it was only a test.

**Hook:** Set a `PostToolUse` hook on the `Edit|Write` matcher that runs `npm run lint`. It reacts rather than prevents, since linting is fast feedback, not something that should block an edit outright — the goal is that a convention slip (like an unused variable) surfaces immediately instead of at review time. Triggered it deliberately by asking Claude to add an unused `leftover` variable to `routes/health.js`; the debug log confirmed the hook ran `eslint` right after the edit and reported the `no-unused-vars` warning. Reverted that test edit afterward.

**Headless task:** Ran a docs-vs-code audit headless: "check whether `docs/api.md` matches the actual routes, report any drift, don't change anything." Locked `--allowedTools` down to the `docs` MCP server's read-only tools plus `Read`/`Grep` — no `Edit`, `Write`, or `Bash` at all, since this task only ever needed to look at files, never touch them. It came back clean (docs match the code), and because nothing writable was in the allowed set, there was no way for it to have done anything else even if it had tried.
